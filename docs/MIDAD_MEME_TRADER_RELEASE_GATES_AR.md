# MIDAD Meme Trader — بوابة الجودة والإصدار

**المنتج:** MIDAD Meme Trader  
**معرّف Android:** `ai.midad.meme.trader`  
**قناة الإصدار الحالية:** Internal / APK قابل للتجربة  
**قاعدة أساسية:** لا يُعلن عن APK جاهز للتثبيت أو يُرسل إلى Dropbox قبل اجتياز بوابة الإصدار كاملة.

## 1. قواعد التشغيل التي لا تتجاوزها أي نسخة

1. **Audit → Verify → Preserve → Repair → Integrate → Upgrade.** لا إعادة بناء من الصفر، ولا استبدال مكوّن عامل دون إثبات الحاجة.
2. **لا أسرار داخل APK أو GitHub أو الواجهة.** لا مفاتيح خاصة، ولا عبارات استرداد، ولا مفاتيح خدمة Supabase أو مفاتيح منصات تداول داخل التطبيق. اتصالات التنفيذ المستقبلية تمر عبر خدمة خلفية محدودة الصلاحيات.
3. **افتراضيًا Paper Trading فقط.** يجب أن تبقى معاملات البلوكتشين وتوقيع المحفظة وإرسال أوامر تداول حقيقية مغلقة إلى أن يجتاز مسار التنفيذ تدقيقًا أمنيًا مستقلًا، وتتاح موافقة بشرية صريحة قبل أول تنفيذ حقيقي أو أي إجراء مالي لا يمكن عكسه.
4. **لا تساوِ بين الزخم والأمان.** كل عملة غير مثبت سلامة عقدها تُعرض بوضوح على أنها غير متحققة. غياب نتيجة مزود الأمان لا يتحول إلى نتيجة آمنة.
5. **لا ادعاءات ربح مضمونة.** تصنيف الفرص لا يعد وعدًا بالربح. يجب أن تُحسب النتائج بعد الرسوم والانزلاق والضرائب/التكاليف ذات الصلة متى أمكن قياسها.
6. **لا نشر صامت لنسخة فاشلة.** أي فشل في اختبار أو توقيع أو التحقق من هوية الحزمة يوقف التسليم ويصدر تقريرًا واضحًا.

## 2. بوابة ما قبل البناء

- التحقق من manifest: اسم المنتج، `app_id`، الإصدار، المدخل، الأصول، وميزانيات الخصائص.
- تشغيل `node mobile/factory/quality-gate.mjs midad-meme-trader`.
- فحص صياغة جميع ملفات JavaScript المرتبطة وإشارات الأسرار.
- التحقق من أن مراجع CSS/JS والصور في HTML تتطابق مع الأصول التي تنسخها عملية Factory إلى حزمة Android.
- اختبارات قواعد التصنيف باستخدام بيانات مصطنعة: هبوط حاد → DUMP_RISK، اندفاع مفرط → EXHAUSTION_RISK، سيولة ناقصة → LIQUIDITY_RISK، وحالة زخم معتدل وسيولة كافية → MOMENTUM_WATCH أو OBSERVE حسب بقية الشروط.
- اختبار حالات انقطاع الشبكة، مهلة الاتصال، استجابة مزود غير صالحة، صفر نتائج، وبيانات سعر قديمة؛ يجب أن تظهر رسالة مفهومة وألا تتحول البيانات الناقصة إلى إشارة إيجابية.

## 3. بوابة التداول الورقي

- التحقق من حساب الكمية، الرصيد، الرسوم الافتراضية والانزلاق السعري في الدخول والخروج.
- وقف الخسارة وجني الربح يعملان على سعر حديث متاح؛ **لا إغلاق آلي اعتمادًا على سعر قديم**.
- يمنع فتح مركز ورقي جديد عندما تكون إشارة الأصل عالية الخطر أو السيولة أدنى الحد.
- اختبار تحديث الرصيد والربح المحقق وغير المحقق وسجل العمليات وCSV بعد الشراء والإغلاق.
- حفظ قائمة المراقبة والسجل محليًا مع التعامل الصحيح مع فشل التخزين.
- التأكد أن زر «شراء ورقي» لا يتصل بمنصة أو محفظة ولا يرسل أي معاملة حقيقية.

## 4. بوابة بناء Android

- بناء `assembleRelease` بنجاح.
- التحقق من توقيع APK عبر `apksigner verify`.
- التحقق من معرّف الحزمة وإصدارها واسم المنتج، وليس من نجاح البناء وحده.
- توليد SHA-256 مستقل للـAPK وتقرير build/test.
- فحص نهائي للأصول داخل الحزمة وسلامة واجهة Android على شاشة صغيرة.
- حفظ قناة البناء بوضوح: Internal/Debug أو Production. المفتاح المؤقت الذي ينشأ لكل بناء **للتجارب فقط**، ولا يعد استراتيجية توقيع إنتاج قابلة للترقية. قبل توزيع عام، يجب استخدام مفتاح توقيع ثابت داخل GitHub Secrets أو مخزن أسرار آمن ذي صلاحيات محدودة؛ لا يوضع المفتاح في المستودع أو Dropbox.

## 5. بوابة واجهة وتجربة الاستخدام

- واجهة عربية RTL أولًا، بخط واضح، أزرار قابلة للمس، ومسافات مناسبة لهاتف Android.
- لكل شاشة حالة تحميل، وحالة خالية، وحالة خطأ، وطريقة واضحة للتعافي.
- إظهار وقت آخر تحديث، مصدر البيانات، وحدود دقة تصنيف المخاطر.
- عدم حجب المحتوى بنافذة منبثقة، وعدم الاعتماد على دخول Control Room لكي يعمل التطبيق المستقل.
- الحفاظ على استهلاك الشبكة والبطارية؛ لا حلقات مسح غير محدودة عند الخلفية.
- اللغة العربية هي الافتراضية؛ التوطين إلى الإنجليزية والفارسية بوابة إصدار محددة لا يُعلن عنها كمكتملة قبل اختبار الشاشة والنصوص فعليًا.

## 6. بوابة Dropbox والتسليم

بعد نجاح جميع البوابات السابقة فقط:

1. رفع APK وتقرير البناء/الاختبار وملف SHA-256 إلى `/MIDAD/Mobile Apps/` باسم يتضمن المنتج والإصدار.
2. التحقق من الملف في Dropbox عبر الاسم والحجم وتاريخ التعديل.
3. مقارنة SHA-256 الخاص بالملف المستلَم مع SHA-256 الذي خرج من عملية البناء إذا كان مسار النقل يتيح فحصه؛ إن تعذر ذلك، يُسجل التحقق كـPENDING ولا يُدّعى التطابق.
4. الاحتفاظ بنسخة GitHub Actions artifact كتاريخ للبناء، مع رابطها ومعرّف الـcommit.
5. عدم استبدال ملف إصدار سابق. كل إصدار ملف جديد قابل للتمييز والرجوع إليه.
6. تسجيل النتيجة بوضوح: **PASS / FAIL / PENDING**. لا تُسمّى النسخة «جاهزة للتثبيت» إلا إذا اكتمل التوقيع وفحص الحزمة والتسليم.

## 7. موافقات التنفيذ

- أعمال القراءة العامة، التحليل، تصنيف المخاطر، التداول الورقي، الاختبارات، الإصلاحات القابلة للمراجعة، وإنشاء تقارير المنتج يمكن أن تسير بصورة استباقية ضمن الصلاحيات الممنوحة.
- نشر عام، معاملات حقيقية، توقيع/نقل أموال، ربط مفاتيح منصة، أو أي خطوة مالية لا رجعة فيها تتطلب بوابة أمان مستقلة وموافقة بشرية صريحة.
- لا يُطلب من المستخدم إرسال كلمة مرور أو مفتاح خاص أو عبارة استرداد داخل المحادثة.
