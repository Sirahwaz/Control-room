Your checkout isn't done when the invoice is created.

A practical checklist for separating payment requests, verified receipts and order fulfillment—before a silent state mismatch becomes an accounting problem.

The key principle

An invoice means a payment was requested. A verified receipt means the payment evidence matches the intended transaction. A fulfilled order means the promised work was delivered. These are separate facts and should be stored, verified and displayed separately.

Three states, three different questions

When a buyer reports “I paid, but the order still says pending,” the first task is to identify which state failed to advance. A resilient design does not let one state stand in for another.

01 / PAYMENT INTENT

What was requested?

The expected amount, asset, network, recipient address and expiry. It is a quote or request—not proof of funds received.

02 / VERIFIED RECEIPT

What actually arrived?

An independently observed transaction matching the amount, asset, network, recipient and required chain evidence or finality.

03 / ORDER FULFILLMENT

What was delivered?

The order’s business lifecycle: awaiting payment, paid, in progress, needing input, delivered or cancelled. “Paid” is not the same as “delivered.”

Where silent checkout failures come from

1. Two database writes, only one succeeds

A service might save a payment intent, then fail while creating the order. The result is an orphan record and a customer-facing flow that has no reliable order to follow. Where the records must exist together, create them in one database transaction or a single atomic operation, and verify the returned identifiers.

2. Duplicate events or repeated requests

Webhooks retry. Users refresh. Browsers repeat a request after a timeout. Idempotency keys and uniqueness constraints should make a repeated request safe, without producing duplicate orders or counting the same receipt twice.

3. The receipt is detected, but not fully reconciled

A transaction hash alone is not enough. Check the intended asset and network, the exact recipient, the quoted amount in base units, transaction evidence, confirmation/finality rules and whether the receipt has already been assigned to another order.

4. Payment and order status drift apart

Even after a verified payment state is recorded, updating the related order may fail. Reconciliation needs an idempotent way to repair that mismatch and an audit trail explaining whether it succeeded or requires manual review.

5. The status screen tells the wrong story

A status endpoint can reject a request that the front end assumes is supported; or it can return only the order status while hiding that payment verification is still pending. Every action button needs a matching API contract, and the response should distinguish payment state from delivery state.

Safety rule: if payment evidence is ambiguous, stop at “review required.” Do not ask the buyer to pay again simply because one internal state failed to update.

The evidence-first checkout checklist

  • ✓Atomic creation: create the intent and order together; check that their IDs and product details match.
  • ✓Strong order reference: bind a high-entropy order key to exactly one order. Reject malformed and unknown keys without returning customer data.
  • ✓Exact receipt matching: verify asset, network, recipient, exact quoted amount, transaction identity and required chain evidence.
  • ✓Idempotent reconciliation: retries should converge on one result; duplicates or contradictory evidence should be routed to review.
  • ✓Order-state synchronization: after verification, update the matching order safely and confirm the persisted result.
  • ✓Separate payment and delivery: do not mark work delivered merely because the receipt is verified.
  • ✓Privacy at the status endpoint: return only what the customer needs. Never expose other customers’ contact details or requirements.
  • ✓Safe test plan: verify malformed keys, unknown orders, duplicate requests and update failures without sending funds or creating a paid test order in production.

What a useful diagnostic should produce

A useful report does more than say “the checkout looks fine.” For each finding, record the affected state, the evidence that supports it, a reproducible way to trigger the issue, the expected result, the observed result and the smallest safe next step. Where a path cannot be tested without a real payment or production side effect, say so explicitly rather than pretending the end-to-end test passed.
